# Server runtime

Production startup is owned by the root `bedriox.cmd` and `bedriox` launchers.
They invoke only the adjacent qualified PHP Runtime. Before Composer autoload,
`bootstrap/bedriox.php` verifies the external manifest trust pin, target ABI,
PHP configuration, exact extension set, and complete runtime inventory. This is
an installation-integrity boundary, not a sandbox for a malicious local binary.

`ServerRuntime` is the bounded, non-blocking composition boundary between RakNet, the protocol-2193 session, and the authoritative simulation. Each call to `poll()` performs at most the configured datagram, lifecycle-event, payload, packet, command, streaming, and world-tick work. Older protocol requests fail during network negotiation.

The runtime accepts application payloads only from a ready RakNet session using `ReliableOrdered` delivery on ordering channel zero. A `SessionOpenedEvent` creates one login channel. Successful login transfers the authenticated identity, verified client appearance, and both live cipher directions exactly once to a play channel. Once the initialization bootstrap has been released, the player is admitted when the client returns `SetLocalPlayerAsInitialized` with the assigned runtime entity ID and the authoritative simulation accepts the queued join. A duplicate acknowledgement for that entity is an idempotent no-op. Terrain delivery continues independently, so valid movement and chat received after that acknowledgement cannot be rejected merely because SubChunk responses remain queued. Duplicate identity, duplicate session, and full-world rejections close only that pending peer.

StartGame advertises the new inventory system so retail moves and splits use authoritative item-stack requests instead of legacy prediction-only transactions.

Post-login batches remain encrypted and zlib-negotiated. The play channel bounds compressed and decompressed bytes, packet count, command count, and queued output. It converts negotiated-version `PlayerAuthInput`, chat, initialized own-actor emotes, fixed-flat block actions, hotbar selection, main-inventory/cursor stack requests, and grass placement into immutable simulation commands. Accepted peer movement uses `MoveActorAbsolute`; authoritative owner correction uses `MovePlayer` reset mode. Movement translation uses Protocol's semantic jump and posture flags, compares the full unsigned client tick before assigning a bounded protocol-neutral local sequence, and projects the predicted feet position and velocity. Stale client ticks have no movement effects. The simulation owns one active break target per player and advertises the 18-tick empty-hand grass progress rate. Predicted completion is revalidated against authoritative reach, the current block, breakability, and sequence instead of using packet-arrival timing as an authorization gate; accepted completion atomically replaces the canonical state, while invalid or racing predictions receive owner correction. Future tool effects must derive from the current server-held item. Continue-destroy input starts the next authoritative target. Crack events and accepted changes reach only players whose delivered chunk view contains the target. A retail abort-break action is targetless: the channel normalizes its sentinel position and face before command creation, and the simulation clears the active target without validating invented coordinates. Each player owns a fixed 36-slot inventory, a cursor, and one 64-count grass stack in selected slot zero. Take, Place, and Swap requests from dedicated packets or embedded PlayerAuthInput are staged and committed atomically against authoritative slots; failures return an error and full correction. A placement transaction first selects its bounded hotbar slot, then placement validation reads only the server-owned selected stack and authoritative world. Client item descriptors, counts, auxiliary values, stack-network IDs, item block runtime IDs, target runtime IDs, reported player position, and prediction fields remain bounded reconciliation hints; they neither authorize nor veto a placement. The clicked block and face remain bounded intent that the simulation validates against canonical world state. The simulation validates clicked state, reach, face, empty destination, and every player collision before changing the world and decrementing the authoritative stack exactly once. Rejection restores both involved blocks and the authoritative held slot. Unrelated typed inventory transactions remain notification-only. Client collision hints remain non-authoritative. Untrusted chat attribution fields are ignored. Emote duration, XUID, platform ID, and flags are discarded; the simulation rate-limits the UUID intent and the adapter relays it only to peers with the authenticated runtime actor, zero duration, empty external identifiers, and server-side muted-chat flags. Chunk-radius requests are clamped to the configured maximum radius. Unexpected packets, subclients, reliability modes, entity IDs, malformed batches, cipher failures, or queue overflow close only the affected session.

Block mutations are durable only for the current process. Movement collision queries those latest canonical states, so breaking support permits the client's next bounded falling prediction and placing a block immediately contributes collision. Current admitted terrain states use either an empty shape for air or a full-cube shape; partial block shapes remain future work.

Routine notifications cross the boundary only after Protocol has decoded and bounded a typed packet. Retail-observed Interact, own-entity Animate and EmoteList, and client-cache status may arrive before initialization and are harmless no-ops. After initialization, own-entity equipment selects an authoritative hotbar slot; unrelated player actions, container-close notices, ability requests, inventory-layout options, and unsolicited network-latency notifications remain no-ops because their gameplay systems are outside the MVP. Validated Take, Place, and Swap requests for main inventory, hotbar, and cursor enter the authoritative simulation; stale or unsupported requests receive an error and bounded correction without disconnecting the session. Bedriox does not originate latency probes and therefore does not invent a response flow without retail evidence. Wrong-entity equipment/action/animation/emote lists, premature post-spawn-only notifications, unknown packet types, and malformed typed payloads close only that session.

Simulation positions use feet coordinates. The protocol adapter applies the Bedrock eye-height offset in one place for clientbound StartGame, AddPlayer, and MovePlayer positions and reverses it for validated serverbound prediction. Clientbound movement derives its on-ground bit from authoritative terrain support. Terrain-constrained input commits the resolved server position, resets only the owner's prediction, and sends the same resolved actor transform to visible peers. Other prediction rejection uses Bedrock reset mode rather than teleport mode and leaves state unchanged.

Authenticated display names are revalidated at the simulation boundary and must fit the 16-character, 64-byte player-name limit. A valid authentication proof containing a name outside the gameplay limit closes only that session before world admission.

Simulation ticks produce authoritative join, movement, correction, chat, emote, and disconnect events. `BedrockWorldEventPacketEncoder` projects those events back into protocol packets. Join publishes player-list membership in both directions. A bounded runtime visibility registry introduces an actor only after its chunk has been sent to that recipient, using the ordered `PlayerList` membership, complete-metadata `AddPlayer`, and authenticated `PlayerSkin` sequence. The introduction already carries the actor's current transform, so movement fan-out omits only recipients introduced during that same event and resumes normally on the next movement. Leaving the sent view removes the actor without removing player-list membership, and returning republishes the actor without duplicating the list entry. Posture transitions follow absolute visible-peer movement as actor metadata deltas. Disconnect projection sends `RemoveActor` to current viewers before `PlayerListRemove`. Transport callbacks never mutate world state directly.

The signed client-data JWT's bounded `DeviceOS` claim is retained privately with authenticated login state for trusted server-side diagnostics. It remains a client-reported claim, not proof of physical hardware. Peer-facing `PlayerList` and `AddPlayer` packets always use the protocol's unknown build platform value, matching the privacy-preserving behavior of the reference servers and avoiding incompatible login-versus-wire enum domains.

`ConnectedTransport` permits deterministic tests; `DiscoveryServerTransport` is the production adapter for `RakNet`. The adapter drains RakNet's separate bounded pre-ready diagnostic queue after each poll and, only when protocol tracing is enabled, maps its observed endpoint, stage, stable reason, identifiers, length, reliability, and ordering channel into structured JSON. It never receives packet bodies, GUIDs, embedded addresses, authentication material, or exception messages; diagnostic saturation is reported without affecting admission or lifecycle capacity. Runtime shutdown is idempotent, clears login/play cryptographic state, closes transport state, and requests priority simulation cleanup for every joined player. A world-event encoding or fan-out budget failure disconnects only the session whose command caused that event; an ownerless event failure closes the runtime because it cannot be attributed safely. Play rejection, channel close, isolated transport failure, and top-level runtime failure paths emit bounded JSON diagnostic events containing only allowlisted reason, packet-ID, phase, event-type, and exception-class fields. They never include exception messages, tokens, JWTs, keys, raw encrypted payloads, packet bodies, or client-provided attribution. Diagnostic writer failures are ignored and cannot alter server behavior.

Retail compatibility is not implied by this runtime. The initialization packet sequence, data artifacts, and two-client player lifecycle must pass automated interoperability and retail-client qualification before a Bedrock version is listed as supported.

## Launch boundary

`php bin/bedriox serve` composes the production runtime. It creates and then loads `bedriox.settings` from the working directory, applies explicit CLI overrides last, and converts every value into an immutable `ServerConfig` before any network bind. The settings boundary caps the file at 64 KiB and 256 lines and rejects malformed, duplicate, unknown, partial, noncanonical, and out-of-range input. `ServerConfig` strictly bounds identity, literal IPv4 bind and port, player limit, level and chunk-streaming controls, runtime diagnostics, optional all-or-none spawn coordinates, and explicit `FULL` or `SELF_SIGNED` authentication. FULL is the default and completes mandatory JWK discovery before binding UDP. `SELF_SIGNED` cannot be selected implicitly and always emits an unmistakable insecure-development warning. SIGINT and SIGTERM request graceful shutdown where PHP exposes process-control signals; runtime destruction remains fail-closed on other platforms.

The composition root builds the typed Bedrock advertisement through Protocol and passes only its bounded encoded payload plus the explicit accepting-connections policy to RakNet. Protocol owns the exact MCBE fields and verified `Survival;1` semantics; RakNet owns unconnected ping/pong framing and does not interpret Minecraft fields. The configured name, MOTD, maximum players, server ID, and ports are validated before bind.

During play initialization, a valid self-owned inventory-window `MobEquipment` notification is bounded to one pending hotbar slot. Newer valid notifications replace the pending value without queue growth; no simulation command or peer broadcast occurs until the authenticated initialization acknowledgement releases admission. Spoofed actors and malformed wire data remain session-local failures.

Before bind, the composition root loads and verifies the protocol-2193 registry view. It builds Bedriox's process-local canonical block registry, resolves the fixed-flat internal palette, and keeps network runtime IDs behind a translator. Jigsaw and voxel-shape registries, StartGame with the configured level name and spawn, 98 data-driven block properties and required experiments, and the item registry are sent first. After the bounded client radius request, Bedriox clamps the radius to `chunks.view-distance`, publishes the current view center, and drains the remaining registries and player state across bounded runtime polls.

Terrain then flows through the Bedriox-owned `World`, deterministic `FlatWorldGenerator`, bounded `ChunkRepository`, generic Bedrock chunk serializer, and one `ChunkViewManager` per session. Complete columns are generated and sent nearest-first under both per-tick generation and send limits. The configured spawn-radius square must be delivered before `PlayerSpawn`; the remainder of the negotiated view continues afterward. Each column contains complete air sections below the platform and bedrock, two dirt layers, and grass at Y=60 through Y=63. Authoritative simulation movement across a 16-block boundary updates the publisher position, releases columns which left the view, and queues only the newly visible edge. Disconnect releases every retained column. The cache limit must accommodate every configured player view, preventing later sessions from exhausting a cache held by earlier players.

Full streamed columns do not ask the retail client for separate sections, so SubChunk requests are rejected on the production world-streaming path. `SetLocalPlayerAsInitialized` releases authoritative admission exactly once after `PlayerSpawn` and the client's acknowledgement.
