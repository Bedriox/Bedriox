# Server runtime

When protocol tracing is enabled, a failed item-stack request decode records its packet ID, bounded action type and index, byte offset, and fixed failure category. The trace excludes raw packet bytes, item names, and user data; it does not change the session's fail-closed behavior.

Creative item-stack requests accept bounded craft-results advisories after a server-catalog selection without trusting the client's reported result. Block-item drops preserve their network block state independently of whether that item is currently placeable. Mining and destruction effects are filtered to recipients who have received the affected chunk.

Dropped-item movement uses the same absolute-position projection as other visible actors, plus motion updates when the server-owned velocity changes materially or reaches zero. The current Bedrock delta packet's `Ticks` field is an interpolation duration, not the server's elapsed simulation tick; it is not used for item motion.

Production startup is owned by the root `bedriox.cmd` and `bedriox` launchers.
They invoke only the adjacent qualified PHP Runtime. Before Composer autoload,
`bootstrap/bedriox.php` verifies the external manifest trust pin, target ABI,
PHP configuration, exact extension set, and complete runtime inventory. This is
an installation-integrity boundary, not a sandbox for a malicious local binary.
The launchers also bind `OPENSSL_CONF` to the adjacent relocatable provider
configuration. Server composition generates one P-384 key before opening the
world or binding UDP, then reuses that qualified key factory for retail
handshakes so an unjoinable listener cannot appear online.

`ServerRuntime` is the bounded, non-blocking composition boundary between RakNet, the protocol-2193 session, and the authoritative simulation. Each call to `poll()` performs at most the configured datagram, lifecycle-event, payload, packet, command, streaming, and world-tick work. Older protocol requests fail during network negotiation.

The runtime accepts application payloads only from a ready RakNet session using `ReliableOrdered` delivery on ordering channel zero. A `SessionOpenedEvent` creates one login channel. Successful login transfers the authenticated identity, verified client appearance, and both live cipher directions exactly once to a play channel. Once the initialization bootstrap has been released, the player is admitted when the client returns `SetLocalPlayerAsInitialized` with the assigned runtime entity ID and the authoritative simulation accepts the queued join. A duplicate acknowledgement for that entity is an idempotent no-op. Terrain delivery continues independently, so valid movement and chat received after that acknowledgement cannot be rejected merely because SubChunk responses remain queued. Duplicate identity, duplicate session, and full-world rejections close only that pending peer.

StartGame advertises the new inventory system, the persisted player game mode, and the current data-driven creative catalog so retail moves, splits, drops, and creative selection use authoritative item-stack requests instead of prediction-only mutations. Creative groups use Bedrock's zero-based indexes and every non-air descriptor carries the canonical empty item extra-data structure. Opening the player inventory allocates a bounded dynamic window ID, synchronizes all server-held slots and the cursor, and closes the same window conversation.

The item-actor protocol trace records bounded actor IDs and whether an actor was shown, hidden after leaving a delivered chunk, picked up, or expired. It does not include raw item packets or inventory contents; paired inventory-request diagnostics distinguish a rejected drop from an actor that spawned and later disappeared.

Post-login batches remain encrypted and zlib-negotiated. The play channel bounds compressed and decompressed bytes, packet count, command count, and queued output. It translates movement, chat, own-actor emotes, block actions, hotbar selection, authoritative inventory requests, creative selection, item use, attacks, and respawn readiness into immutable simulation commands. Client item descriptors, counts, stack IDs, runtime IDs, positions, and prediction fields remain reconciliation hints; server-owned players, inventories, catalogs, and world state decide every mutation. Break progress derives from canonical block hardness and the selected server-held tool, while successful changes project block-specific particles or sounds and survival drops through chunk-scoped item actors. Main-inventory, cursor, and creative-output actions stage and commit atomically or return bounded correction. Movement, actor, block, and item events reach only sessions with the required delivered chunk or actor view. Unexpected packets, subclients, reliability modes, entity IDs, malformed batches, cipher failures, or queue overflow close only the affected session.

Current entity-attack transactions are an explicit exception to notification-only inventory traffic. The adapter discards client position, click-vector, item and stack claims, retaining only authenticated attacker, bounded target actor ID and hotbar intent. The simulation resolves the target and owns every PvP decision. Accepted hits project authoritative health, hurt animation and composed actor motion with the target's exact latest client input tick only to the target and viewers. Death presentation uses bounded raw-system or translated-system text: localized vanilla reasons are broadcast to joined players, while the independently configurable death-screen reason is sent only to the victim. Game-mode changes use the retail owner/peer split: the owner receives its game type, abilities, adventure settings, and creative resynchronization in order, while viewers receive only the actor game-type update and visibility reconciliation.

Block mutations are durable only for the current process. Movement collision queries those latest canonical states, so breaking support permits the client's next bounded falling prediction and placing a block immediately contributes collision. The built-in generation palette has a complete process-local collision registry shared by player and dropped-item resolution. It distinguishes empty vegetation and fluids, full cubes, and bounded partial geometry such as snow layers, paths, farmland, cactus, bamboo, panes, bars, lanterns, dripstone, mud, and soul sand. A generated state without an explicit definition fails startup tests, while an unexpected runtime gameplay state is corrected to the affected player instead of terminating the process.

Routine notifications cross the boundary only after Protocol has decoded and bounded a typed packet. Retail-observed Interact, own-entity Animate and EmoteList, and client-cache status may arrive before initialization and are harmless no-ops. After initialization, own-entity equipment selects an authoritative hotbar slot; unrelated player actions, ability requests, inventory-layout options, and unsolicited network-latency notifications remain no-ops because their gameplay systems are outside the MVP. Validated Take, Place, Swap, and Drop requests for main inventory, hotbar, and cursor enter the authoritative simulation; legacy and item-stack drop forms converge on the same atomic server-owned removal and entity spawn. Stale or unsupported requests receive an error and bounded correction without disconnecting the session. Bedriox does not originate latency probes and therefore does not invent a response flow without retail evidence. Wrong-entity equipment/action/animation/emote lists, premature post-spawn-only notifications, unknown packet types, and malformed typed payloads close only that session.

Simulation positions use feet coordinates. The protocol adapter applies the Bedrock eye-height offset in one place for clientbound StartGame, AddPlayer, and MovePlayer positions and reverses it for validated serverbound prediction. Clientbound movement derives its on-ground bit from authoritative terrain support. Terrain-constrained input commits the resolved server position, resets only the owner's prediction, and sends the same resolved actor transform to visible peers. Other prediction rejection uses Bedrock reset mode rather than teleport mode and leaves state unchanged.

Authenticated display names are revalidated at the simulation boundary and must fit the 16-character, 64-byte player-name limit. A valid authentication proof containing a name outside the gameplay limit closes only that session before world admission.

Simulation ticks produce authoritative join, movement, correction, chat, emote, and disconnect events. `BedrockWorldEventPacketEncoder` projects those events back into protocol packets. Join publishes player-list membership in both directions. A bounded runtime visibility registry introduces an actor only after its chunk has been sent to that recipient, using the ordered `PlayerList` membership, complete-metadata `AddPlayer`, and authenticated `PlayerSkin` sequence. The introduction already carries the actor's current transform, so movement fan-out omits only recipients introduced during that same event and resumes normally on the next movement. Leaving the sent view removes the actor without removing player-list membership, and returning republishes the actor without duplicating the list entry. Posture transitions follow absolute visible-peer movement as actor metadata deltas. Disconnect projection sends `RemoveActor` to current viewers before `PlayerListRemove`. Transport callbacks never mutate world state directly.

The signed client-data JWT's bounded `DeviceOS` claim is retained privately with authenticated login state for trusted server-side diagnostics. It remains a client-reported claim, not proof of physical hardware. Peer-facing `PlayerList` and `AddPlayer` packets always use the protocol's unknown build platform value, matching the privacy-preserving behavior of the reference servers and avoiding incompatible login-versus-wire enum domains.

`ConnectedTransport` permits deterministic tests; `DiscoveryServerTransport` is the production adapter for `RakNet`. The adapter drains RakNet's separate bounded pre-ready diagnostic queue after each poll and, only when protocol tracing is enabled, maps its observed endpoint, stage, stable reason, identifiers, length, reliability, and ordering channel into structured JSON. It never receives packet bodies, GUIDs, embedded addresses, authentication material, or exception messages; diagnostic saturation is reported without affecting admission or lifecycle capacity. Runtime shutdown is idempotent, clears login/play cryptographic state, closes transport state, and requests priority simulation cleanup for every joined player. A world-event encoding or fan-out budget failure disconnects only the session whose command caused that event; an ownerless event failure closes the runtime because it cannot be attributed safely. Play rejection, channel close, isolated transport failure, and top-level runtime failure paths emit bounded JSON diagnostic events containing only allowlisted reason, packet-ID, phase, event-type, and exception-class fields. They never include exception messages, tokens, JWTs, keys, raw encrypted payloads, packet bodies, or client-provided attribution. Diagnostic writer failures are ignored and cannot alter server behavior.

`PlayerConnectionDirectory` binds a public immutable player snapshot to that identity's current live play session without exposing the session itself. A handle follows a reconnect to the newest session and a stale disconnect cannot revoke the replacement. Typed packets sent through `PlayerConnection` enter the same bounded play-channel encoder, compression, encryption, and transport path as server-owned output. A normal send is drained on the next runtime poll; an immediate send flushes the current session queue synchronously. Closing the session invalidates existing handles before simulation cleanup.

An authenticated duplicate identity is rejected with a reliable encrypted Bedrock disconnect packet, leaving the original runtime session intact. Explicit player kicks follow the same packet-before-close path. Runtime/player state is removed immediately and the RakNet endpoint stays alive for up to ten seconds to retransmit the reason; the endpoint is removed sooner if the peer closes. RakNet idle expiry separately releases silent established peers and its stable close reason is recorded in protocol diagnostics.

Joining clients receive commands filtered by player sender support and the authenticated UUID's current permissions. `CommandRequestPacket` is accepted only after initialization with a player origin and non-internal intent. Its UUID is replaced with the session's authenticated UUID before dispatch. The runtime uses the same bounded registry, permission checks, cancellable pre-event, and observational post-event as the console, then returns bounded `CommandOutputPacket` feedback on that session. Unknown, denied, malformed, or early command input cannot grant authority or mutate simulation state.

Retail compatibility is not implied by this runtime. The initialization packet sequence, data artifacts, and two-client player lifecycle must pass automated interoperability and retail-client qualification before a Bedrock version is listed as supported.

## Launch boundary

`php bin/bedriox serve` composes the production runtime. It creates and loads user-facing `server.properties` and advanced `bedriox.settings`, then applies explicit CLI overrides and converts every value into an immutable `ServerConfig`. Each file is capped at 64 KiB and 256 lines with a strict independent key allowlist. Malformed, duplicate, unknown, partial, noncanonical, and out-of-range input fails closed. After parsing, the composition root applies and verifies the configured main-process memory limit before starting logging, workers, persistence helpers, authentication discovery, world services, or networking. FULL authentication remains the default; explicit self-signed mode always emits an unmistakable insecure-development warning. SIGINT and SIGTERM request graceful shutdown where PHP exposes process-control signals; runtime destruction remains fail-closed on other platforms.

The composition root builds the typed Bedrock advertisement through Protocol and passes only its bounded encoded payload plus the explicit accepting-connections policy to RakNet. Protocol owns the exact MCBE fields and verified `Survival;1` semantics; RakNet owns unconnected ping/pong framing and does not interpret Minecraft fields. The configured name, MOTD, maximum players, server ID, and ports are validated before bind.

During play initialization, a valid self-owned inventory-window `MobEquipment` notification is bounded to one pending hotbar slot. Newer valid notifications replace the pending value without queue growth; no simulation command or peer broadcast occurs until the authenticated initialization acknowledgement releases admission. Spoofed actors and malformed wire data remain session-local failures.

Before bind, the composition root loads and verifies the protocol-2193 registry view. It builds Bedriox's process-local canonical block registry, resolves the gameplay and selected-generator palettes, and keeps network runtime IDs behind a translator. Jigsaw and voxel-shape registries, StartGame with the authoritative persisted level name and spawn, data-driven block properties and required experiments, and the item registry are sent first. After the bounded client radius request, Bedriox clamps the radius to `view-distance`, publishes the current view center, and drains the remaining registries and player state across bounded runtime polls.

Terrain then flows through the Bedriox-owned `World`, selected deterministic generator, bounded `ChunkRepository`, shared worker-backed prepared-envelope cache, and one `ChunkViewManager` per session. Complete visible columns are generated and sent nearest-first under count, elapsed-time, transfer-byte, and compressed-byte budgets. Workers translate immutable canonical revisions, encode `LevelChunk`, frame the batch, and compress it; the main process revalidates the exact revision before session encryption and transport. Matching players share one in-flight task and cache entry, while unfinished chunk work never enters their ordered output queues. Only after the visible square is prepared may the configured hidden ring consume generation capacity; it remains unsent until movement promotes a prefetched column into view. The configured spawn-radius square must be delivered before `PlayerSpawn`; the remainder of the negotiated view continues afterward. `default` supplies seeded three-dimensional terrain, the complete admitted biome registry, fluids, caves, aquifers, ores, vegetation, and deterministic structures; `flat` retains the exact bedrock/dirt/grass profile. Authoritative simulation movement across a 16-block boundary updates the publisher position, promotes prepared columns, releases columns which left the retained area, and queues only newly missing work. Disconnect releases every retained column. The authoritative cache limit must accommodate every configured player view including its hidden ring, preventing later sessions from exhausting a cache held by earlier players; the compressed prepared cache is bounded independently by entries and bytes.

Full streamed columns do not ask the retail client for separate sections, so SubChunk requests are rejected on the production world-streaming path. `SetLocalPlayerAsInitialized` releases authoritative admission exactly once after `PlayerSpawn` and the client's acknowledgement.
